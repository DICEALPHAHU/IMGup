# ImgUp

**插件自带图片上传网站。** 玩家在网页上传图片，在游戏里用 `/imgup` 确认上传码，
然后用地图把图片贴出来。

整个网站跑在插件进程里 —— 单个 jar，不需要 Docker、不需要 Python、不需要 RCON，
也没有 `shared_secret`。网页和插件直接内存通信。

English: [README.en.md](README.en.md)

---

## 为什么用它

原版流程下，玩家想把一张图贴到游戏里，得自己把图片文件放进服务端目录、再敲指令，
还要自己注意命名格式和文件类型。对普通玩家来说这一步基本劝退。

ImgUp 把这一步变成：**打开网页 -> 选图 -> 上传 -> 进游戏敲一次上传码**。
之后的文件名、缩放、格式转换、审核都是自动的。

几个设计取舍：

- **不上传文件到外部服务。** 图片只存在你自己的服务器上。
- **玩家身份绑在游戏里。** 网页上生成的 8 位上传码必须在游戏内用 `/imgup` 确认，
  所以「网页上的玩家名」是可信的，不需要让玩家注册账号。
- **文件名自动符合 `<玩家ID>-<图片名>` 格式。** 很多服务端对图片命名有要求，
  插件直接按这个格式生成，玩家不用记规则。
- **只收 PNG / JPG。** 动图和 PDF 会被拒；PDF 尤其重要 —— 它本身不是图片，
  但有插件漏洞可以让它被当成图片处理。
- **图片只缩放、不放大。** 小图不会被拉糊，也不会被当成高清图浪费地图空间。
- **永远重新编码。** 不管上传什么，都会用 ImageIO 重新编码，顺带丢掉 EXIF
  之类的元数据，也避免「图片里夹带脚本」这类问题。

## 环境要求

| 项目 | 要求 |
| --- | --- |
| 服务端 | Paper / Purpur，API `26.3.build.194-stable`（其它相近版本一般也能用） |
| Java | 21 或更高 |
| 配套插件 | [Images](https://github.com/Andavin/Images)（Custom Images）—— 真正把图片贴进游戏的那个插件，见「[与 Images 插件的关系](#与-images-插件的关系)」 |

> 没装 Images 插件时插件仍然能启动，只是图片会存到自己的数据目录，
> 游戏里 `/image create` 找不到它们，日志里会给出提示。

## 安装

1. 把 `ImgUp-<版本>-<git短哈希>.jar` 放进服务端的 `plugins/` 目录。
2. 启动服务端。首次启动会：
   - 生成 `plugins/ImgUp/config.yml`
   - 生成一个随机的后台管理密码，**打印在控制台和日志里**
   - 在配置的端口上启动网站
3. 打开 `http://<你的服务器IP>:<端口>`，确认页面能出来。

如果玩家要从外网访问，记得在**防火墙 / 云服务商安全组**里放行这个端口。

> **一定要填 `web.public_base_url`。** 它决定「发给玩家的地址」和「复制出来的
> 图片链接」。留空时会退化成用 `web.host` + 端口拼，而默认的 `web.host` 是
> `0.0.0.0`，拼出来就是 `http://127.0.0.1:8091` —— 只有服务器自己点得开。
> 这种配置下启动时会打印一条警告提醒你。

## 使用流程

玩家侧：

1. 打开网站，点「获取上传码」，拿到一个 8 位码（默认 5 分钟内有效）。
2. 进游戏，在聊天框输入 `/imgup <上传码>`。
3. 网页会自动检测到确认，然后就能选图上传了。
4. 上传完成后网页会给出一条游戏内指令，复制它。
5. 在游戏里粘贴执行，手持地图按提示右键，图片就贴上去了。

> **上传页会提示图片比例。** Minecraft 的地图是正方形的，非正方形的图贴上去
> 会被拉伸或留白。上传页常驻一行说明，选中非正方形的图片时还会按它的实际
> 宽高再提醒一次 —— 只是提示，不会阻止上传。

管理员侧：

- 游戏内：`/imgup list` 看待审列表，`/imgup ok <文件名>` 通过，
  `/imgup no <文件名> [原因]` 拒绝。
- 网页后台：`http://<地址>/admin`，用配置里的 `web.admin_password` 登录，
  可以批量审核、删除、按状态筛选。

## 指令与权限

| 指令 | 别名 | 说明 |
| --- | --- | --- |
| `/imgup <上传码>` | | 确认网页上生成的上传码 |
| `/imgup list [页码]` | `ls` | 列出待审核的图片（带分页） |
| `/imgup ok <文件名>` | `approve`、`pass` | 通过审核并发布 |
| `/imgup no <文件名> [原因]` | `reject`、`deny` | 拒绝（原因会显示给玩家） |
| `/imgup del <文件名>` | `delete`、`rm` | 删除图片 |
| `/imgup info` | `status` | 查看网站运行状态 |
| `/imgup reload` | | 重新读配置、重载语言文件、**重启网站** |

> `/imgup reload` 会把网站停掉再按新配置起一遍，所以**改端口不需要重启服务端**。
> 停机时会给正在上传的请求留 2 秒宽限期，不会直接掐断。

| 权限 | 默认 | 说明 |
| --- | --- | --- |
| `imgup.use` | 所有人 | 允许确认上传码 |
| `imgup.admin` | OP | 允许审核、删除、重载 |

## 配置

配置文件是 `plugins/ImgUp/config.yml`，每一项都有中英双语注释。改完用
`/imgup reload` 生效。

### 网站

| 配置项 | 默认 | 说明 |
| --- | --- | --- |
| `web.enabled` | `true` | 关掉就完全不开放端口 |
| `web.port` | `8091` | 网站监听端口 |
| `web.host` | `0.0.0.0` | 监听地址。只想本机访问就填 `127.0.0.1` |
| `web.public_base_url` | 空 | **对外的访问地址**，强烈建议填。留空的后果见「安装」一节 |
| `web.site_name` | `CustomImagesUp` | 页头品牌名，也用在浏览器标签页标题上 |
| `web.auto_publish` | `true` | 上传后直接发布。关掉则先进待审队列 |
| `web.admin_enabled` | `true` | 是否开放 `/admin` 后台 |
| `web.admin_password` | 随机生成 | 网页后台的密码，首次启动会打印 |
| `web.icp_license` | 空 | 备案号。填了页脚最底部会显示，并链到工信部备案查询页 |
| `web.request_timeout_seconds` | `60` | 请求体的**空闲**超时。客户端挂着不发数据超过这个时间就断开 |

### 图片

| 配置项 | 默认 | 说明 |
| --- | --- | --- |
| `upload.max_upload_bytes` | `5242880` | 单张图片体积上限（5 MB） |
| `upload.max_dimension` | `2048` | 最长边缩放上限（只缩不放） |
| `upload.max_pixels` | `16000000` | 总像素上限，防解压炸弹。**这一项直接决定内存峰值**，见下 |
| `upload.jpeg_quality` | `90` | JPEG 编码质量 |
| `upload.max_name_length` | `64` | 生成的文件名长度上限 |
| `upload.max_nickname_length` | `32` | 玩家填的图片昵称长度上限 |

> **`upload.max_pixels` 和内存的关系：**
> 峰值内存 ≈ `max_pixels × 4 字节 × limits.max_concurrent_uploads`。
> 默认值下是「单张解码约 64 MB、8 并发约 0.5 GB」。要放宽它，请同时调小
> `max_concurrent_uploads`。实测过：一张 **123 KB** 的纯色 PNG（远低于 5 MB
> 体积上限）就能让堆增长一百多 MB —— 体积小不代表解码后小。

### 限额

| 配置项 | 默认 | 说明 |
| --- | --- | --- |
| `limits.per_player_daily` | `20` | 每个玩家每天的上传张数 |
| `limits.global_pending_max` | `200` | 待审队列上限，满了就不让再传 |
| `limits.max_concurrent_uploads` | `8` | 同时处理的上传数，`0` 表示不限制 |
| `limits.newcode_per_ip_per_hour` | `30` | 每个 IP 每小时能领几个上传码 |
| `limits.login_per_ip_per_hour` | `10` | 每个 IP 每小时允许几次后台登录**失败** |

> 登录限流**只统计失败次数**，所以正常登录、登出不会被自己挡住；
> 被限流期间即使密码是对的也不放行。

### 其它

| 配置项 | 默认 | 说明 |
| --- | --- | --- |
| `language` | `zh` | 默认语言 |
| `messages_dir` | `messages` | 语言文件目录 |
| `site.allow_rename` | `true` | 允许玩家给待审核的图片改名 |
| `code_ttl_seconds` | `300` | 上传码有效期 |
| `require_permission` | `false` | 上传是否要求 `imgup.use` 权限 |
| `notify_player` | `true` | 审核结果是否在游戏内通知玩家 |

> `web.icp_license` 是按中国大陆的备案要求做的：**留空时页脚完全不出现这一行**，
> 填了才会显示，并且是可点击的（按惯例做成不显眼的样式，看起来就是普通文字）。

## 语言文件

页面文字、报错提示、状态说明、以及玩家在游戏聊天框里看到的消息，
全部放在 `plugins/ImgUp/messages/<语言>.yml`。内置中文和英文两份。

- **改文案**：直接改对应的值，`/imgup reload` 生效。
- **加一门语言**：把 `zh.yml` 复制成 `jp.yml`，把值换成日文即可。
  网页右上角的语言开关会自动多出这一项，显示名取自文件里的 `meta.name`。
- **玩家进游戏的消息**按玩家客户端的语言显示。
- 语言文件里可以用反引号标行内代码，网页上会渲染成 `<code>`：
  ```yaml
  site.footer_note: "服务器：`{motd}`，游戏内贴海报需要 `images.command.create` 权限。"
  ```

**升级不会覆盖你改过的值。** 插件升级时只会把新增的键补进去，
已有的翻译原样保留；万一重载失败（比如目录读不到），也会保留上一份能用的文案，
而不会把整站文字变成键名。

## 安全

这个网站默认是**公网可访问**的，所以几点说明：

- **待审和被拒的图片不公开。** `/preview/<文件名>` 只有后台管理员和**这张图的
  上传者**能取，其他人一律 404。已发布的图才是公开的。
- **后台 cookie 带 `HttpOnly` 和 `SameSite=Lax`**，密码比较用常数时间算法，
  登录失败有按 IP 的限流。
- **上传码必须游戏内确认**，而且 5 分钟就过期，所以网页上填的玩家名不可伪造。
- **连接不会被挂死。** 请求体读取有空闲超时；同时进行的上传数有上限，
  超出的直接返回「稍后再试」，而不是先收下几 MB 再排队。
- **所有上传都会重新编码**，元数据（含 EXIF）会被丢掉。

如果你把后台密码手动改成了弱密码，请注意 `limits.login_per_ip_per_hour` 是你
唯一的兜底。

## 从源码构建

不依赖 Maven / Gradle，只需要 JDK 的 `javac` / `jar` 和 Python 3：

```bash
bash build.sh
```

产物在 `target/ImgUp-<版本>-<git短哈希>.jar`。

首次运行会用 `fetch-deps.py` 把 Paper API 及其编译依赖下载到 `.build-cache/`，
之后离线也能编译。想换缓存位置就设环境变量 `IMGUP_BUILD_CACHE`。

`build.sh` 除了编译打包，还会跑一批产物校验，任何一项不过就直接失败。
这些校验都是被真实踩过的坑逼出来的，比如：

- 语言文件的键是否一致、有没有死键、非中文语言里有没有漏译的中文
- 模板里有没有硬编码的可见中文（英文界面会漏出来）
- 页面引用的 `$msg_` 占位符和 `/static/` 资源是否都存在
- `web/` 下每种静态资源的扩展名有没有对应的 `Content-Type` 分支
- 配置项和代码是否双向对得上（config 里有没有死配置、代码读的键有没有声明）
- SVG 资源是不是合法 XML

## 一些实现说明

**HTTP 服务器用的是 JDK 自带的 `com.sun.net.httpserver`**，配虚拟线程执行器。
没有引入任何网络框架，所以产物就是单个 jar，运行时除了服务端本身不带任何依赖。

**上传的图片直接写进 Images 插件的数据目录**，因为 `/image create` 只认那个目录。

审核索引是插件自己的，所以**启动时会把磁盘上有、索引里没有的图片补登记回来**：
不止 ImgUp 自己写的 `pending/`、`rejected/`，还包括 Images 数据目录根下的图 ——
也就是装上 ImgUp 之前就已经存在的图、或者后来手动丢进去的图。这些会以「已发布」
状态出现在后台列表里，可以直接审核、删除、复制链接，不用再手动翻目录。

补登记时会从文件名反推 `<玩家>-<图片名>`（只认合法的 Minecraft 用户名，推不出来就留空），
创建时间取文件的修改时间，宽高只读文件头拿，不解码像素，所以一百多张图也只多花几十毫秒。

**网站只监听你配置的端口。** `web.enabled: false` 时完全不开放任何端口。

## 与 Images 插件的关系

ImgUp 自己**不会**把图片贴进游戏 —— 那一步是
[Images](https://github.com/Andavin/Images)（Custom Images，作者
[Andavin](https://github.com/Andavin)）在做，`/image create` 就是它的指令。
ImgUp 补的是它前面缺的那一段：**让玩家自己能把图片传上来**。

分工大致是：

| | 负责什么 |
| --- | --- |
| [Images](https://github.com/Andavin/Images) | 读取服务端目录里的图片文件，把它渲染到地图上 |
| ImgUp | 提供网页让玩家上传图片、自动生成合规的文件名，写进 Images 的数据目录 |

两个插件是搭配使用的：ImgUp 存进去的图片，`/image create` 直接就能用。

ImgUp 没有复制 Images 的任何实现，也不碰它的配置文件。唯一的耦合是通过
Bukkit 拿到它的数据目录（`getPlugin("Images").getDataFolder()`），把图片放进去。
这也是为什么 Images 升级、换版本都不影响 ImgUp。

> Images 是 Andavin 的独立项目，有问题请去它的仓库反馈，不要算在
> ImgUp 头上（反过来也一样）。没装它的时候 ImgUp 仍然能启动，
> 只是图片会落到自己的数据目录里。
